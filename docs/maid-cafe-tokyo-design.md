## 0. 要約 / Summary

**日本語**
- maid-cafe.tokyo は「メイドカフェ風の先生」が英会話・Web/スマホアプリ開発・学校の勉強・研修を教える学習サイト。落ちこぼれ対策(難しければ問題を易しくし、しつこくない程度に反復)を中核にする。
- 既存資産を統合する: **maid-cafe-english**(旧open-english。先生UI・多言語・ニュース取得・カリキュラム連携)+ **realdata.pro**(Rust製の列指向分析エンジン・CSV取込・世界リサーチ)+ **aruaru-search / aruaru-llm**(無料メタ検索・小型AI)。土台は RPoem(Rust)。
- ニュース・知識は「要約+出典URL+日付」必須、全文転載なし、根拠が無ければ「分からない」と答える。
- データ分析は API/公式ダウンロード優先、ToS と robots.txt を順守。デスクトップ版は手元のCSVを大量に扱う。
- 配備は ConoHa VPS + HTTPS + systemd timer による毎朝の自動更新。
- 実装は **RPoem の保守完了後**(条件は §9.1)。

**English**
- maid-cafe.tokyo is a learning site where a maid-café-style tutor teaches English conversation, web/mobile development, school subjects and corporate training, with a "no one left behind" loop (lower difficulty when a learner struggles, gentle spaced repetition).
- It merges maid-cafe-english (formerly open-english), realdata.pro (Rust in-memory analytics) and aruaru-search/aruaru-llm on top of RPoem.
- News/knowledge answers always carry a summary, source URL and date; no full-text copying; the system must be able to say "I don't know".
- Data analysis prefers official APIs/downloads and respects ToS and robots.txt; a desktop build handles large local CSVs.
- Deployment: ConoHa VPS, HTTPS, daily auto-update by systemd timer.
- Implementation does not start until RPoem maintenance is done (§9.1).

## 2. 目的と対象

### 2.1 目的
「メイドカフェ風の先生」が、誰も置き去りにせず、楽しく学べる場を提供する。同時に、世界のニュース・公開データを根拠付きで調べて分析できる道具を、無料または低コストで提供する。

### 2.2 科目(段階順)
1. 英会話(最優先。既存の資産が最も厚い)
2. Web開発・スマホアプリ開発(maidcafe-programming-school のカリキュラムを継承)
3. 学校の勉強(小中高。教科は後で選定)
4. 研修(教室):企業・団体向けの接客/英語/IT研修。機能は「教室(クラス)・課題配布・進捗確認」から始める

### 2.3 利用者
学習者(個人)、講師・教室運営者、調べものをする人(個人・中小企業)、情報提供先(政府・コンサル・調査会社。無料提供。§4.5)。未成年が含まれるため個人情報は最小限にする(§10)。

## 3. 落ちこぼれ対策:出題・難易度制御

### 3.1 設計原則
- 「できない」を責めない。**間違いは情報**として扱い、難易度を下げる合図にする。
- しつこくしない:同じ問題の連続出題を避け、1セッションの復習は上限を設ける。
- 学習者が操作できる:「簡単にする/難しくする/今日はやめる」ボタンを常に表示。自動調整は提案として透明に表示する(なぜ下げたかを説明)。

### 3.2 データモデル(概念)
- `skill`(例: 英語・過去形、JS・for文)…学習項目の最小単位。前提関係のグラフ(前提が弱ければ先に戻る)
- `item`(問題)…skill、難易度 d(1〜10)、形式、正解、誤答への助言
- `attempt`…正誤、回答時間、ヒント使用、自己評価(「自信あり/なし」)、日時
- `learner_skill`…推定習熟度 m(0〜1)、連続失敗数、最終出題日、次回出題日

### 3.3 ロジック(初期案。パラメータは実測で調整)
1. **出題**: 習熟度 m が 0.6〜0.85 になる難易度を狙う(易しすぎず難しすぎない帯)。
2. **難しいと判断する条件**(いずれか): 同skillで直近3問中2問以上不正解/ヒント多用+不正解/回答時間が基準の3倍超が2回/学習者の「難しい」申告。
3. **対応**: 難易度を1〜2段下げる→それでも失敗なら前提skillへ戻る→別の説明形式(例・図・音声)に切替。メッセージは励まし方向で、不正解の連打を避ける。
4. **反復(間隔反復)**: 正解の間隔を 1日→3日→7日→14日… と延ばし、誤答は短い間隔(翌日)で再出題。**1日の復習上限**(例: 10問)と**同一問の再出題間隔の下限**(同セッション内は再出題しない)を設ける。
5. **上げる条件**: 直近5問中4問以上正解かつ回答時間が基準内。
6. **燃え尽き防止**: 3回連続で下げても失敗する場合は出題を止め、休憩/別skillを提案し、講師・教室運営者に任意で通知(本人同意時のみ)。

### 3.4 検証
- 純関数のロジックとして実装し、ユニットテストで「シナリオ表」を網羅(連続不正解→難易度低下→回復→上昇)。
- シミュレーション(仮想学習者)で、出題がしつこすぎない/下がりすぎない/上がらなすぎないを確認。
- 実利用での指標: 継続日数、同一問の平均再出題回数、離脱率。

## 4. ニュース・知識の取り込みと出典付き回答

### 4.1 取り込み
- 取得元は優先順に、(1)公式API/RSS/オープンデータ、(2) aruaru-search 経由の公開検索結果の**見出し・URL・日時**。記事本文は保存しない。
- 毎日の取り込みジョブ(systemd timer)で、国別・テーマ別に見出し、要約(後述)、出典URL、取得日時、公開日、発行元、言語を保存。
- 既存の `archive-policy.json` 方式(許可リスト・fail closed)を継承: 見出し+リンクは公開可、他社の抜粋は非公開、会話は常に非公開。

### 4.2 回答の必須要件
1. すべての事実主張に、**出典URL+記事の日付+取得日**を付ける。
2. 要約は自分の言葉で、原文より十分短く。**全文転載・長い引用をしない**(引用は短く出典明示)。
3. 出典が見つからない/矛盾する場合は「**分かりません/確認できません**」または「出典Aは〜、出典Bは〜と食い違っています」と答える。推測は推測と明示する。
4. 日付が古い情報は「◯年◯月時点」と表示し、更新日が古ければ警告する。
5. 数値は原典の単位・時点・定義を併記する。

### 4.3 AIの使い方(小型AIの限界を前提に)
- 現行の無料AI(aruaru-llm)は小型で品質が限定的。**事実はAIの記憶ではなく取得した出典から**答える(検索→根拠抽出→要約の順)。
- 検証層: 回答中の各文に対応する出典スニペットがあるかを機械的に確認し、無い文は削除または「根拠なし」と表示。数値と固有名詞は出典内に実在するか文字列照合する。
- モデルは差し替え可能にする(無料の自前/外部API/高性能モデルを利用者が選択。既存の AI選択肢の方針を継承)。

### 4.4 世界情勢・知識
ニュース以外(百科的知識)は、Wikipedia/Wikidata(CC BY-SA/CC0)、政府・国際機関の公開文書を優先し、ライセンスと帰属を保存する。

### 4.5 政府・コンサル・調査会社への無料提供と誤情報対策
- 提供物は「**要約+出典+日付+信頼度ラベル**」のレポート形式。原典を差し替えず、原典へ導く。
- 信頼度ラベル(例: 公的一次情報/報道機関/二次情報/未検証)を出典の種別から機械的に付与。AIの自信度ではなく**出典の質**に基づく。
- **訂正の仕組み**: 各レポートに版番号と訂正履歴(aruaru-db の `AS OF COMMIT` で過去版を再現)。誤りの連絡窓口を明記し、訂正は公開する。
- **免責**: 助言ではなく情報提供であること、意思決定前に原典を確認することを明記(法的文言は法務確認が必要:未決事項)。
- 配信前に「出典の生存確認(リンク切れ)」「日付」「数値照合」を自動チェックし、失敗した項目は配信しない。

## 5. データ分析機能

### 5.1 機能
- CSV/TSV/JSON/Excel等のアップロード、大容量対応(ストリーミング読込、列指向インメモリ。realdata.pro の `rrd-core` を再利用)。
- クレンジング(欠損・重複)、要約統計、相関、group by、簡単な回帰、グラフ(棒・円・折れ線・ヒストグラム)。
- ダウンロード: 加工後CSV、グラフ画像(SVG/PNG)、レポート(Markdown/PDF)。
- 分析の再現性: 取込元データのハッシュ・取得日・ライセンスをレポートに添付。
- 教材連携: ニュースや公的統計を使った「データを読む練習」を学習機能に組み込む(データサイエンティストコースと接続)。

### 5.2 データカタログ(公開データ源の台帳)
§1.4の20件を初期登録。項目: 提供元、URL、ライセンス、帰属表示、更新頻度、取得方式(API/CSV/スクレイピング不可)、**robots.txtとToSの確認日・結論**、制限(要アカウント等)。台帳に無い/規約が不明なデータ源は取り込まない。

### 5.3 取得ルール
1. **API/公式ダウンロードを最優先**。HTMLスクレイピングは最後の手段で、**ToSで禁止なら行わない**。
2. robots.txt を取得し順守。User-Agent に連絡先を明記。リクエスト間隔を空け、429/403で休止(aruaru-search の流儀を踏襲)。
3. **利用者のURL取込はSSRF対策**(私的IP・メタデータアドレス・リダイレクト先の再検証、サイズ/時間上限)。realdata.pro の実装を再利用して再監査する。
4. 利用者がアップロードしたデータの権利は利用者責任である旨を明示し、アップロード物はその利用者のみに見える(公開しない)。
5. 取り込んだ再配布不可データは、サイト上で公開再配布しない(分析結果の表示は許諾範囲内で)。

### 5.4 ダウンロード版(デスクトップ)
- 目的: 数GB級のCSV、社内の非公開データ、ネット接続なしでの分析。データは端末外に出さない。
- 構成: Tauri(RPoem 経由)+ 同一の分析エンジン。Windows/macOS/Linux。ローカルでの取り込み・集計・可視化はオフライン可、データカタログからの取得のみ通信。
- Web版との差: 容量上限なし(端末依存)、アカウント不要、AIはローカル/利用者設定のものを選択。
- 配布は maid-cafe-se / maid-cafe-english の既存インストーラー・自動更新の仕組みに合わせる。

## 7. 配備(ConoHa VPS)

> 具体的なIP・鍵・トークンは本書に書かない。シークレットはVPS上の環境ファイル(権限600)または systemd credentials に置き、リポジトリには入れない。

### 7.1 構成
```
[利用者] → HTTPS(443) → リバースプロキシ(Caddy または open-web-server)
                             ├─ 静的ファイル(web/)
                             └─ アプリ(RPoem, 127.0.0.1:ポート)
                                  ├─ aruaru-search / aruaru-llm(127.0.0.1)
                                  └─ DB(SQLite/aruaru-db)
```
- DNS: maid-cafe.tokyo(さくらのドメイン)の A レコードを VPS へ(設定中)。`www` は CNAME/301。AAAA はIPv6を使う場合のみ。
- HTTPS: Let's Encrypt(ACME)の自動更新。Caddy なら自動、open-web-server を使うなら自動HTTPS機能の実機確認が必要。HSTSは動作確認後に有効化。
- ファイアウォール: 22(鍵認証のみ・パスワード認証無効)、80、443 のみ開放。内部サービスは 127.0.0.1 のみ。
- 実行ユーザーは非root、systemd ユニットで `NoNewPrivileges`・`ProtectSystem=strict` 等を設定。
- バックアップ: DBと設定(秘密を除く)を日次で退避(既存の vps-backup / aruaru-db-archive 方式を踏襲)。**復旧手順を一度実際に試す**。
- 監視: `/healthz`、ディスク容量、証明書期限、ジョブ失敗をメール通知。

### 7.2 毎朝の自動更新(新バージョンがあれば取り込んで再デプロイ)
systemd timer を採用(cronより、ログ・失敗検知・依存管理が扱いやすい)。

**手順(`maid-update.service` を `maid-update.timer` が毎朝 05:00 JST に起動)**
1. `git fetch` で対象タグ/ブランチ(`release` ブランチまたは最新の署名付きタグ)を確認。差が無ければ終了。
2. 新しい版を別ディレクトリ(`releases/<sha>`)にチェックアウトし、ビルド(またはCIの成果物を取得してハッシュ検証)。
3. テスト/スモーク(`/healthz`、主要ページ、マイグレーション乾式)に合格したら、`current` シンボリックリンクを切替え、サービスを再起動。
4. 再起動後ヘルスチェックに失敗したら**自動で前の版へロールバック**し、通知。
5. DBマイグレーションは前方互換(拡張→移行→削除の順)にし、ロールバック可能にする。
6. 古い `releases/` を最新3つ残して削除。
- 安全策: `main` 直結でなく**CIがgreenのタグのみ**デプロイ。更新ジョブは同時実行をロック(`flock`)。失敗時はメール通知。ビルドに依存する上流(RPoem等)は `deps.lock` のコミット固定を維持し、上流変更は別途ゲート(open-upstream-watch の考え方)を通す。
- ニュース/データ取り込みは別の timer(`maid-news.timer`)にし、更新デプロイと独立させる。

timer の例(概念):
```
[Timer] OnCalendar=*-*-* 05:00:00 Asia/Tokyo ; Persistent=true ; RandomizedDelaySec=300
```

## 8. テスト・デバッグ方針(共通)
- 純ロジック(§3)はユニットテスト+シミュレーション。

- ステージング(`staging.`サブドメインまたは別ポート)で本番前確認。
- ログは個人情報を含めない。エラーは追跡ID付きで保存。
